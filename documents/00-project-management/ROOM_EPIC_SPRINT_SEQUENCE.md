# Room Epic – Sprint Sequence

This document lays out the high‑level sequence of sprints for the **Local Music Queue** room epic.  Each sprint is scoped narrowly and builds upon the preceding work.  As sprints close, their status will be updated in this document along with a short description of the outcome.  If a sprint has not yet been shaped, its goals and requirements are captured in a corresponding stub in the `SPRINTS` folder.

| Sprint | Name | Status | Description |
|---|---|---|---|
| **R00** | Room architecture contract plan | **Closed** | Established the baseline architecture contract for rooms. Defined key domain concepts, roles (host, member, guest), and the high‑level API surface. Captured as ADR 001 and sprint `006-room-architecture-adr-contract-plan`. |
| **R01** | PostgreSQL migration design | **Closed** | Designed the move from an embedded SQLite database to PostgreSQL. Documented migration strategy, updated schemas and connection configuration. Captured as ADR 002 and sprint `007-postgresql-migration-design`. |
| **R02** | Core domain implementation | **Closed** | Implemented initial room domain entities (room, user, membership) and basic REST endpoints. Laid groundwork for future sprints by scaffolding repository interfaces and service layers. |
| **R03** | SQLite → PostgreSQL data migration | **Closed** | Performed a one‑time migration of all persistent data from SQLite to PostgreSQL. Added migration scripts, validated data integrity and adjusted CI pipelines accordingly. |
| **R04** | Room invites and membership lifecycle | **Closed** | Added support for inviting users to a room, accepting/declining invites, leaving a room and transferring ownership. Introduced roles (owner vs. member) and access control for invite and join operations. |
| **R05** | Session token authentication | **Closed** | Introduced per‑user session tokens for authenticating both REST and WebSocket calls. Added middleware to resolve a user from a session token, updated the invite/join flows to issue tokens, and tightened CORS. |

Three small post-acceptance UX/logging follow-ups landed on `dev` (commits `e9fc1a2`, `5e27789`, `b01dec0`) — Options-page token-status badge refresh, dashboard clipboard-failure catch hardening, and removal of an unapproved plan file. Documented in `011-player-lease-and-host-departure-semantics.md` (Implementation summary + Verification Results sections). |
| **R07** | Room‑scoped playback queue | **R07a closed (2026-06-29); R07b closed (2026-06-29); R07c closed (2026-06-29); R07d closed (2026-06-30); all accepted by the Product Owner; rest split/deferred** | R07a landed per-room queue persistence plus the four room-scoped REST endpoints (add/remove/clear/get). R07b landed the additive per-room WebSocket sync/delta events at `GET /ws/rooms/{slug}` and the `roomqueue.Broadcaster` seam, plus fixes to the per-room hub keepalive (added ping ticker), register/sync ordering (hub-loop linearisation of seq allocation), and the matching documentation. R07c landed the narrow authenticated frontend wiring (`/rooms/:slug` route + minimal `RoomView.vue`; four `api.*Room*` REST methods; dedicated `room-websocket.js` client with sequence-gap recovery via REST; isolated `globalStore.roomQueues` slice) against the R07a/R07b contracts without changing backend behavior. R07d landed one room-scoped queue mutation: `POST /api/rooms/{slug}/queue/prioritize`, the matching `room_queue_song_prioritized` per-room WebSocket delta, and a minimal RoomView Prioritize control (host/admin only), with tightened closure-pass invariants (`*int` request shape so missing `song_index` returns 400; interactor returns the post-mutation song so the broadcast payload carries `is_prioritized: true`). No changes to global queue behavior or the global `/ws` contract were made. Remaining R07 scope (relational queue rows, room-scoped arbitrary drag-and-drop reorder, room-scoped voting, cross-process safety, migration of the legacy global `queue_state` into a room) remains split and deferred to subsequent slices. The original R08 placeholder ("Public read-only API and CORS") is deferred/renumberable; it is NOT what R07b shipped. See sprint `012-room-scoped-playback-queue.md`. |
| **R08** | Public read‑only API and CORS | **Planned** | Expose read‑only endpoints for external clients to fetch room state (queue, player status) without requiring full authentication. Implement strict CORS policies and caching headers. See sprint `013-public-read-only-api-and-cors.md`. |
| **R09a** | Lease-aware room playback controls | **Accepted (2026-06-30)** | First narrow slice of R09. Adds four lease-holder-only room playback mutations — `POST /api/rooms/{slug}/playback/{status,sync,skip,ended}` — plus three additive per-room WebSocket events (`room_playback_status_changed`, `room_playback_elapsed_sync`, `room_playback_song_advanced`) on `/ws/rooms/{slug}` and a minimal RoomView Play/Pause/Skip/Ended control surface. Lease enforcement at the use-case layer via a new `room.PlaybackLeaseAuthorizer` seam implemented by `PlayerLeaseInteractor.RequireActiveLeaseHolder`. The global `/api/queue/...` contract, the 16-event global `/ws` inventory, voting, auto-queue, public API/CORS, Docker, and auth remain untouched. See sprint `014-player-control-semantics.md` Implementation summary (R09a). |
| **R09b** | Room vote-to-skip backend contract | **Accepted (2026-06-30)** | First narrow slice of the legacy R09b+ bucket. Adds `POST /api/rooms/{slug}/vote/skip` (behind `roomAuth`), the additive per-room WS events `room_vote_updated` + `room_vote_resolved`, a unique-connected-presence counter on `*RoomWSHub`, and reuses the existing `room_playback_song_advanced` event with `reason: "skip"` on a passed vote. Sessions live in `internal/usecase/roomvote` — in-memory, room-scoped, current-song-scoped, 30-second expiry, single-instance only. Threshold = `max(2, uniqueConnectedUserCount / 2 + 1)` captured at session creation. Wire updates: production-time ExpireSessions runner is now ticking on /ws/rooms/{slug} via a server-owned adapter; the room-vote broadcast payload sanitises the session through a RoomVoteSessionDTO that omits VotedBy so `voted_by` is never sent to clients. Empty queue / no current song maps to `400 Bad Request`. The global `/api/vote/...`, global `/api/queue/...`, global `/ws` 16-event inventory, priority balances, auto-queue, Docker, CORS, auth, and frontend UI remain untouched. See sprint `014-player-control-semantics.md` Implementation summary (R09b). |
| **R09c** | Room-scoped volume command | **Closed (2026-07-01, accepted by the Product Owner)** | First narrow slice of the legacy R09c+ bucket. Adds one lease-holder-only room-scoped command — `POST /api/rooms/{slug}/playback/volume` with body `{"direction":"up"|"down"}` — plus one additive per-room WebSocket event (`room_playback_volume_changed`) on `/ws/rooms/{slug}`. Lease enforcement at the use-case layer via the existing `room.PlaybackLeaseAuthorizer` seam (R09a). Volume is intentionally NOT persisted: there is no PostgreSQL migration, no `room_queue_state` JSON shape change, no `entity.Queue.Volume` field, and the command does not call `queueRepo.Save`. The global `/api/queue/volume` contract, the 16-event global `/ws` inventory, voting, auto-queue, public API/CORS, Docker, and auth remain untouched. The closure pass tightened two narrow UX details on `dev`: the frontend toast on `room_playback_volume_changed` now uses an explicit up/down branch (a non-up/down payload reads as a neutral "Volume changed." rather than silently defaulting to "decreased"); and the WS hub test file ends with a trailing newline matching the rest of the suite. See sprint `014-player-control-semantics.md` Implementation summary (R09c). |
| **R09d** | Room-scoped previous playback command | **Closed (2026-07-01, accepted by the Product Owner)** | Second narrow slice of the legacy R09c+ bucket (the original `prev` slice from the R09 sprint stub). Adds one lease-holder-only room-scoped command — `POST /api/rooms/{slug}/playback/prev` (empty body) — plus one additive per-room WebSocket event (`room_playback_song_previous`) on `/ws/rooms/{slug}`. Lease enforcement at the use-case layer via the existing `room.PlaybackLeaseAuthorizer` seam (R09a). The command requires a valid current song and `CurrentIndex > 0`; on success it decrements `CurrentIndex`, sets `Elapsed = 0`, sets `Status = playing`, and persists the room queue. On no-current-song or already-first-song the command returns `400` with no mutation, no save, and no broadcast. Lease sentinels map to 403/404/410/409 per the R09a contract; archived rooms map to 409. A new `entity.Queue.PrevToPrevious` helper mirrors `AdvanceToNext`'s no-partial-mutation invariant and a local `roomqueue.ErrNoPreviousSong` sentinel is added so the handler maps cleanly to 400 without string-matching the legacy `Queue.Prev()` error. Auto-queue is NOT triggered. The global `/api/queue/prev` contract, the 16-event global `/ws` inventory, voting, priority balances, Docker, CORS, and auth/session design remain untouched. A minimal frontend `Prev` control is gated on the existing lease-holder UI affordance AND on `current_index > 0` (UI convenience only; backend is authoritative). See sprint `014-player-control-semantics.md` Implementation summary (R09d). |
| **R09e** | Room auto-queue contract design | **Closed (2026-07-01, accepted by the Product Owner)** | Third narrow slice of the legacy R09c+ bucket (the room auto-queue shape from the R09 sprint stub). R09e is a **documentation-only** planning/design sprint that shapes a narrow, reviewable contract for a future room auto-queue implementation. R09e introduces **no** Go runtime code, **no** Vue runtime code, **no** migrations, **no** routes, **no** WebSocket constants, and **no** config changes. The contract settles: per-room scope (room-scoped, NOT silently controlled by the global auto-queue config), per-room persistence (per-room config + history tables or a documented equivalent), reuse of the existing `domain.RelatedSongFetcher` abstraction, a future `roomautoqueue.Interactor` orchestrator that uses a coordinator `mu` mutex guarding a per-room `inFlight` map keyed by room id/slug (NOT a single global `triggering` flag) and that NEVER holds a lock during the slow `FetchRelated` call, queue-owned conditional insertion + stale revalidation in `roomqueue.Interactor`, a per-room `room_auto_queue_added` event on `/ws/rooms/{slug}` only (the global `/ws` 16-event inventory is unchanged), per-room single-flight concurrency with cross-room independence mirroring the global auto-queue's Sprint 004 hardening, zero-side-effect stale-candidate handling (no save, no history, no activity, no broadcast), host/admin toggle authorization, failure semantics, and a full future test matrix. Single-instance only; no cross-process safety claim. The future room auto-queue runtime implementation is the next R09e+ slice and remains deferred. See sprint `021-room-auto-queue-contract-design.md`. |
| **R09f** | Room auto-queue backend runtime | **Closed (2026-07-01, accepted by the Product Owner)** | Fourth narrow slice of the legacy R09c+ bucket (the room auto-queue runtime). R09f is a **backend-only** runtime implementation that conforms to the R09e contract. R09f lands two REST endpoints (`GET /api/rooms/{slug}/autoqueue/status` for any active member; `POST /api/rooms/{slug}/autoqueue/toggle` for host/admin only) behind `roomAuth`; two per-room WebSocket events (`room_auto_queue_added`, `room_auto_queue_config_changed`) on `/ws/rooms/{slug}` only — the global `/ws` 16-event inventory remains byte-for-byte unchanged; a new `internal/usecase/roomautoqueue` package that orchestrates per-room config read + yt-dlp recommendation fetch + queue-owned conditional insertion + history append + per-room broadcast; per-room auto-queue persistence via migration `0007_room_auto_queue` (`room_auto_queue_config` + `room_play_history` with the same 50-row per-room cap as the global `play_history`); a queue-owned conditional insertion seam in `roomqueue.Interactor.AddRoomAutoQueueSong` that returns `roomqueue.ErrRoomAutoQueueStale` on any violation with zero side effects (mirrors the global `queue.AddAutoQueueSong` contract byte-for-byte); a non-blocking `CheckAndTrigger` wired into `PlaybackEnded` / `SkipPlayback` / `SkipVote` / `RemoveSong` / `ClearQueue` only when the post-mutation queue ends at `current==last`; a per-room `inFlight` map guarded by a coordinator mutex whose critical section is narrow enough to preserve cross-room independence (the slow FetchRelated call is held outside any lock); a typed narrow broadcaster seam (the production wiring connects the use case to `*ws.RoomWSHub.BroadcastRoomAutoQueueAdded` directly, carrying the full R09e payload tuple — room_slug, song, source_song_title, current_index, current_song, status, elapsed, state); and `SetEnabled` serialized with the post-fetch insertion so a disable landing before the insertion drops the candidate with no queue save, no history append, and no broadcast. The frontend `RoomView` / store / API surface is intentionally deferred (R09f is backend-only per the sprint directive). The global `/api/autoqueue/...` contract, the global `/ws` 16-event inventory, the global `auto_queue_config` / `play_history` tables, the `domain.AutoQueueRepository` / `usecase/autoqueue.Interactor` / `PostgresAutoQueueRepository` / `YtDlpRelatedFetcher`, the global `roomqueue` exclusion of `PrevPlayback` from auto-queue triggers, and the global `queue.AddAutoQueueSong` contract are all unchanged. Authorization is owned at the use-case layer (`GetConfig` is open to any active member; `SetEnabled` requires host/admin via `requireHostOrAdmin`), matching the roomqueue use-case pattern. **Closure pass (2026-07-01):** tightened the `SetEnabled` ↔ `CheckAndTrigger` serialization invariant — `SetEnabled`'s `SaveConfig` write now runs under the same coordinator `mu` that the post-fetch recheck + `AddRoomAutoQueueSong` insertion hold, so a `SetEnabled(false)` save can no longer interleave between the final "still enabled?" check and the queue mutation. `GetConfig` (and the rest of the slow paths in both methods) remains outside the mutex; the critical section is the minimum needed to serialize the disable write with the post-fetch decision window. The package-level `Locking discipline` comment and the `Interactor.mu` doc reflect the new serialization surface. The disabled-mid-flight test was replaced with two tests that pin the locked-correct outcomes directly — `TestSetEnabled_SerializedWithPostFetchCriticalSection` (RED-fails without the lock; asserts `SaveConfig` does not enter while the add fn holds mu, then proceeds after release) and `TestSetEnabled_RunsBeforePostFetchRecheck_DropsCandidate` (asserts the other valid outcome: `SetEnabled(false)` committed before the post-fetch recheck → recheck observes disabled and drops, no add fn call, no queue mutation, no broadcast, no history append). No global queue/playback/voting/auto-queue, frontend, Docker, migration, or REST contract changes. See sprint `021-room-auto-queue-contract-design.md` (Implementation summary (R09f)). |

## How to use this document

* When shaping a new sprint, refer to the stub file listed in the **Description** column.  Each stub provides a goal, describes the baseline behaviour, outlines desired changes, lists the affected context and gives implementation guidance.
* Once a sprint completes, update the **Status** in the table to **Closed** and summarise the outcome.  If any decisions change the scope of later sprints, reflect that here.
* If you add a new sprint, append it to the bottom of the table with a short description and create a matching stub file under `documents/00-project-management/SPRINTS`.
