Sprint **R10b — Room deletion and membership removal — backend runtime implementation** is **implemented on `dev` (2026-07-02)**; Product Owner acceptance is **pending** for the runtime implementation. R10b is the backend-only runtime implementation that conforms to the accepted **R10a — Room deletion and membership removal — contract design** (Accepted 2026-07-02). R10a is a **documentation-only** contract design sprint: it introduces **no** Go runtime code, **no** Vue runtime code, **no** migrations, **no** routes, **no** WebSocket constants, and **no** config changes. R10a replaces the legacy R10 stub with a narrow, reviewable contract. R10b implements that contract by landing the two HTTP routes (`DELETE /api/rooms/{slug}` host-only soft archive, idempotent on already-archived rooms; `DELETE /api/rooms/{slug}/members/{userId}` host-only member removal with explicit sentinels `ErrHostCannotRemoveSelf` + `ErrCannotRemoveHost` mapped to `400`, `409` on archived rooms, `404` on non-member target), the membership-delete + active-lease-end atomic transaction, the three per-room WebSocket envelopes on `/ws/rooms/{slug}` only — `room_member_removed` (delivered to the removed client before close), `room_members_changed` (delivered to remaining clients), and the per-room-hub `room_archived` broadcast (with `reason: "host_archived"`, reusing the existing R06 wire value + payload via new explicit per-room hub support; the global `/ws` archive broadcast continues to ride the R06 path unchanged) — and a removed-client WebSocket close with code `1008` (policy violation) to distinguish host-driven removal from a benign disconnect. R10b is **backend/runtime only**: no Vue runtime code, no frontend API methods, no frontend store, no RoomView controls, no frontend tests. The frontend UI slice for delete-room / remove-member controls is a separate **R10c** slice and is explicitly **deferred** until R10b is accepted. The R10a contract settles: soft-archive semantics for "delete room" (hard delete / hard purge / cleanup is **out of scope**); host role as the owner equivalent (no new role/owner column); confirmation stance (no body in R10b — confirmed by bearer-token + host role); HTTP status-code mapping with explicit sentinels `ErrHostCannotRemoveSelf` and `ErrCannotRemoveHost` (both mapped to `400`); archived-room behavior; member-removal behavior with immediate loss of room membership; session-token stance (no room-scoped revocation — enforce via membership checks + per-room WS disconnect/notification only); player-lease effects (removed active lease holder has lease ended in the same transaction as the membership delete; room archive ends active lease idempotently via the existing R06 path); room-vote effects (removed user MUST NOT count in future thresholds; active sessions are **left to natural expiry**); an optional audit table shape (R10b does NOT introduce the table); and the Decision 11 test matrix (covered by R10b usecase / HTTP handler / WebSocket hub / race-sensitive tests). Single-instance only; no cross-process safety claim. See [015-room-deletion-and-membership-removal.md](./015-room-deletion-and-membership-removal.md) for the full R10a contract + the R10b Implementation summary section, and [`../ROOM_EPIC_SPRINT_SEQUENCE.md`](../ROOM_EPIC_SPRINT_SEQUENCE.md) for the R10a / R10b / R10c split.

Sprint R09f — Room auto-queue backend runtime — is closed on `dev` (2026-07-01) and accepted by the Product Owner (2026-07-01). R09f is the backend-only runtime implementation of the room auto-queue contract shaped by R09e. R09f adds two REST endpoints (`GET /api/rooms/{slug}/autoqueue/status`, `POST /api/rooms/{slug}/autoqueue/toggle` behind `roomAuth` with host/admin toggle authorization enforced at the use-case layer); two per-room WebSocket events (`room_auto_queue_added`, `room_auto_queue_config_changed`) on `/ws/rooms/{slug}` only — the global `/ws` 16-event inventory remains byte-for-byte unchanged; a new `internal/usecase/roomautoqueue` package that orchestrates per-room config read + yt-dlp recommendation fetch + queue-owned conditional insertion + history append + per-room broadcast; per-room auto-queue persistence (migration 0007_room_auto_queue: `room_auto_queue_config` + `room_play_history` with the same 50-row per-room cap as the global `play_history`); a queue-owned conditional insertion seam in `roomqueue.Interactor.AddRoomAutoQueueSong` that returns `ErrRoomAutoQueueStale` on any violation with zero side effects (mirrors the global `queue.AddAutoQueueSong` contract byte-for-byte); a non-blocking `CheckAndTrigger` wired into `PlaybackEnded` / `SkipPlayback` / `SkipVote` / `RemoveSong` / `ClearQueue` (when the post-mutation queue ends at `current==last`); a per-room `inFlight` map guarded by a coordinator mutex whose critical section is narrow enough to preserve cross-room independence (the slow FetchRelated call is held outside any lock); a typed narrow broadcaster seam (replacing the prior generic-map BroadcastFunc adapter) that the production wiring connects directly to `*ws.RoomWSHub.BroadcastRoomAutoQueueAdded` and that carries the full R09e payload tuple (room_slug, song, source_song_title, current_index, current_song, status, elapsed, state); and `SetEnabled` serialized with the post-fetch insertion so a disable that lands before insertion drops the candidate with no queue save, no history append, and no broadcast. The closure pass tightened the `SetEnabled` ↔ `CheckAndTrigger` serialization invariant on `dev`: `SetEnabled`'s `SaveConfig` now runs under the same coordinator `mu` that the post-fetch recheck + `AddRoomAutoQueueSong` insertion hold, so a `SetEnabled(false)` save can no longer interleave between the final "still enabled?" check and the queue mutation (the prior code resolved room + checked role + called `GetConfig`/`SaveConfig` without ever taking the coordinator mutex). The disabled-mid-flight test was replaced with two tests that pin the locked-correct outcomes directly — `TestSetEnabled_SerializedWithPostFetchCriticalSection` (asserts `SaveConfig` does not enter while the add fn holds mu, then proceeds after release) and `TestSetEnabled_RunsBeforePostFetchRecheck_DropsCandidate` (asserts the other valid outcome: `SetEnabled(false)` committed before the post-fetch recheck → recheck observes disabled and drops, no add fn call, no queue mutation, no history append, no broadcast). The package-level `Locking discipline` comment and `Interactor.mu` doc reflect the new serialization surface; `GetConfig` (and all other slow paths) remain outside the mutex. The frontend `RoomView` / store / API surface remains intentionally deferred (R09f is backend-only). See [021-room-auto-queue-contract-design.md](./021-room-auto-queue-contract-design.md) for the contract and the *Implementation summary (R09f)* section.

The sprint before R09e is **Sprint R09d — Room-scoped previous playback command** (closed 2026-07-01, accepted by the Product Owner 2026-07-01). R09d adds one lease-holder-only HTTP slice (`POST /api/rooms/{slug}/playback/prev`, behind `roomAuth`, empty body), one additive per-room WebSocket event (`room_playback_song_previous`), and a minimal frontend Prev control surface in RoomView (gated on the existing lease-holder UI affordance AND on `current_index > 0`). The command requires a valid current song and `CurrentIndex > 0`; on success it decrements `CurrentIndex`, sets `Elapsed = 0`, sets `Status = playing`, and persists the room queue. On no-current-song or already-first-song the command returns `400` with no mutation, no save, and no broadcast. A new `entity.Queue.PrevToPrevious` helper mirrors `AdvanceToNext`'s no-partial-mutation invariant, and a local `roomqueue.ErrNoPreviousSong` sentinel is added so the handler maps cleanly to 400 without string-matching the legacy `Queue.Prev()` error. Auto-queue is NOT triggered. The global `/api/queue/prev` contract, the global `/ws` 16-event inventory, voting, priority balances, Docker, CORS, and auth/session design remain untouched. See the *Implementation summary (R09d)* section in [014-player-control-semantics.md](./014-player-control-semantics.md).
